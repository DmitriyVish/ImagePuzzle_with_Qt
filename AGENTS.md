# Правила разработки ImagePuzzle

Эти правила действуют для исходного кода и тестов во всём проекте.
Применяй их при написании нового кода и изменении существующего.
Генерируемые файлы в `build/`, включая `ui_*.h`, `moc_*.cpp` и `qrc_*.cpp`, вручную не изменяй.

## Документация Doxygen

- Пиши документационные комментарии в формате **Doxygen** для классов, структур,
  функций и методов, включая значимые приватные методы.
- Используй `/** ... */` перед объявлением и теги `@brief`, `@param`, `@return`
  по применимости. Для конструкторов и функций `void` не добавляй `@return`.
- Описывай назначение, смысл параметров и результата, ограничения, владение объектами,
  требования к потоку и побочные эффекты, если они влияют на использование API.
- Документируй исключения через `@throws` только если они действительно предусмотрены.
  Для ошибок, возвращаемых значением или сигналом, указывай соответствующее поведение.
- Для полей и значений перечислений при необходимости используй `///< ...`.
- Документацию API размещай в заголовке; не дублируй её дословно в реализации.
- Обновляй документацию вместе с изменением поведения. Комментарии пиши на русском,
  сохраняя имена API и идентификаторов без перевода.

## Инлайновые комментарии

- Добавляй `//`-комментарии внутри реализации к нетривиальным участкам кода:
  алгоритмам разбиения, преобразованиям координат, обработке ввода,
  управлению временем жизни объектов и взаимодействию потоков.
- Объясняй причину решения, ограничения, инварианты и пограничные случаи.
  Не ограничивайся пересказом выполняемой строки.
- При изменении логики проверяй актуальность соседних комментариев.

## Логирование

- Добавляй логирование при реализации значимых операций и сценариев:
  запуск приложения, загрузка изображения, генерация и начало пазла,
  завершение игры, сброс состояния и обработка ошибок.
- Используй категории `QLoggingCategory` и функции `qCDebug`, `qCInfo`,
  `qCWarning`, `qCCritical` вместо `printf`, `std::cout` и некатегоризированных логов.
  Именуй категории по подсистеме, например `imagepuzzle.app`, `imagepuzzle.io`,
  `imagepuzzle.puzzle`, `imagepuzzle.input`.
- Выбирай уровень по смыслу: debug — диагностика; info — значимые события;
  warning — восстановимые ошибки; critical — сбои, препятствующие продолжению операции
  или работе приложения.
- Включай контекст, нужный для диагностики: название операции, идентификатор детали,
  количество фрагментов, seed, размеры изображения и описание ошибки — по применимости.
- Не логируй каждое движение мыши, касание или кадр отрисовки. Для частых событий
  используй отключаемую debug-категорию и ограничивай частоту сообщений.
- Не дублируй одну ошибку на каждом уровне вызовов; логируй её там, где есть
  достаточный контекст. Логи не заменяют проверку ошибок и сообщения пользователю.

## Проверка изменений

Перед завершением задачи проверь наличие актуальной Doxygen-документации,
комментариев к нетривиальной логике и логирования значимых операций и ошибок
в добавленном или изменённом коде. Изменения только в документации не требуют
добавления логов или изменения исходников.
